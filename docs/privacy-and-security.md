# Privacy and security model

## Local-first student information

The app stores profile details, academic information, activities, student-specific eligibility assessments, essays, recommendation notes, personal tasks, priorities, tags, free-form notes, and source-evidence revision history in an encrypted local vault in browser IndexedDB. The vault is unlocked by a passphrase before React workspace and Supabase Auth code are loaded.

When a sponsor URL or evidence excerpt changes, the tracker retains a snapshot of the previous public-source URLs and excerpts. The newest 25 revisions are kept per scholarship. This history is included in user-controlled encrypted backups and is not sent to cloud sponsor records.

The local vault encrypts Scholarship Scout student/workspace records with AES-256-GCM. Its key is protected by the user's passphrase with PBKDF2-SHA-256 (600,000 iterations), a random 16-byte salt, and a fresh 12-byte IV per write. Supabase Auth session and PKCE values are stored separately in a dedicated IndexedDB database and encrypted with a non-exportable device-held AES-GCM key; clearing local data removes both stores. The key and decrypted records stay in memory while unlocked. A Web Locks exclusive lock prevents two tabs from opening the same vault simultaneously; the app locks after 15 minutes of inactivity and offers a manual lock control. The legal-acceptance receipt and generic reliability counters remain in localStorage and are not encrypted. Same-origin JavaScript running while unlocked, browser extensions with page access, malware, and an already-unlocked device can still access plaintext in memory. This local vault is at-rest encryption. Encrypted backup files remain a separate export/recovery path.

The app does not upload essays, contact details, school, district, grades, test scores, class rank, activities, or student-specific eligibility to the search service.

## Public discovery and authenticated cloud access

Public live scholarship discovery does not use Supabase Auth and does not create an anonymous Auth user. The browser sends only state, expected graduation year, and selected category IDs to the deployed public `scholarship-discover` function. This function's `verify_jwt=false` setting applies only to that discovery endpoint; it does not grant public access to database tables or other functions.

An authenticated Supabase user is required to read or write cloud scholarship sponsor records. The existing owner policies scope each row to the active user's `auth.uid()`. A read-only policy inspection confirmed that all four public tables use `TO authenticated` owner policies. No policies were changed by this authentication implementation.

Google sign-in is implemented through Supabase Auth OAuth using the `openid email profile` scopes only. The Google OAuth client secret is configured in Supabase Auth Provider settings and is never shipped to the browser. The app returns to the same runtime origin that started sign-in and explicitly uses the PKCE flow. Google and Supabase process the account identity, verified email/basic profile claims, and ordinary authentication/network metadata; the app does not request Gmail, Drive, or other Google API scopes. Google remains unavailable until the existing project's Google provider is enabled with valid credentials and the exact application return URL is allow-listed.

If the active user is an anonymous cloud session, the app calls Supabase `linkIdentity({ provider: 'google' })` rather than starting a separate sign-in. Manual identity linking must be enabled in Supabase. This links Google to the same Auth user ID, preserving existing cloud sponsor-row ownership under `auth.uid()`. If the Google identity already belongs to another account, linking fails; Scholarship Scout does not merge or reassign records automatically.

Student profile and student-specific data remain in the encrypted local vault by default, regardless of cloud account state. If a permanent account explicitly enables cross-device backup, the browser sends only the end-to-end encrypted vault envelope and passkey metadata; it does not send plaintext profile fields or write them to separate profile/eligibility tables. Public discovery does not create a Supabase session or upload those profile details.

## Cloud boundary

The browser Supabase client uses the publishable key only. Its persistent Auth session and PKCE verifier use a separate encrypted IndexedDB adapter protected by a non-exportable device key. Auth storage is not included in cross-device vault snapshots. Student workspace records remain locked until the user opens the local vault.

The current browser API reads and writes the active user's `public.scholarships` sponsor records. The active identity may be an anonymous browser user or an existing permanent account. Cloud fields include scholarship title, sponsor, official HTTPS URL, award range/text, deadline, structured sponsor criteria, evidence references, and verification status. Free-form notes, evidence excerpts, and the local source-evidence revision history are intentionally excluded.

The live database contains `student_profiles`, `scholarship_sources`, `scholarships`, `eligibility_checks`, and `account_vault_backups`. The browser app reads and writes cloud scholarship sponsor records but does not read or write `student_profiles` or `eligibility_checks`; student details and student-specific eligibility assessments remain in the encrypted local vault. The live table grants, RLS state, and managed-role default-privilege findings are recorded under [Database authorization](#database-authorization) below. The opt-in `account_vault_backups` table stores only an end-to-end encrypted envelope, credential identifier, PRF salt, revision, and timestamps. Its RLS policy is restricted to the permanent authenticated owner; anonymous Auth sessions are excluded.

## Optional cross-device encrypted vault

Cross-device backup is off by default and is available only to a permanent signed-in account with an unlocked local vault. Enabling it registers a WebAuthn passkey and derives an AES-GCM wrapping key from the authenticator's PRF output and a random salt. The browser wraps the existing local-vault content key; the account row receives only the encrypted vault envelope, passkey credential ID, PRF salt, and a monotonically increasing revision. The existing passphrase-wrapped content key remains in the envelope as a recovery route. A synced passkey can restore on another device only when the credential provider syncs the credential and the browser/authenticator supports WebAuthn PRF.

The cloud table is owner-scoped with RLS and explicitly excludes anonymous JWT sessions. Sync uses revision compare-and-swap; an out-of-date remote revision pauses sync instead of silently overwriting another device. Local changes made while an upload is in flight remain marked dirty for a subsequent sync. Restore is offered only when the local browser is empty or holds the exact cached ciphertext for that account; unrelated local vault data is never replaced. Supabase auth tokens and PKCE verifiers are deliberately excluded from synced snapshots and must be established by signing in on each device. Deleting the cloud backup does not erase local vaults; deleting the account cascades the account-linked ciphertext row, but does not erase other devices' local copies or downloaded exports.

This is an opt-in encrypted copy of the local workspace, not a cloud-readable profile store. It does not protect plaintext from malicious same-origin code while the vault is unlocked, a compromised browser/device, or an account compromise combined with access to the synced passkey. See the cross-device encrypted-vault design in account-vault-sync.md.

## Search gateway

The client sends only state, expected graduation year, and selected category IDs. The SearXNG gateway URL and bearer token are server-side Edge Function secrets. The function uses a fixed HTTPS gateway base and rejects redirects; the browser does not provide a destination URL.

Supabase reports `scholarship-discover` ACTIVE at version 28 with `verify_jwt=false` for this function only; public discovery does not require a Supabase user JWT. The function remains the only public discovery entry point and receives only state, expected graduation year, and selected category IDs. The authenticated SearXNG gateway enforces its process-wide 30-request-per-minute ceiling. The deployed function inventory also reports `account-delete` ACTIVE at version 4 with `verify_jwt=true`; the deployed bundle was verified to contain `readBoundedJsonBody(request, 2048)` and its shared helper. These version checks do not constitute a fresh end-to-end search or account-deletion request. Cloud scholarship CRUD remains authenticated and owner-scoped.

## Database authorization

The November 28, 2026 read-only production audit found five tables in `public`; all five have RLS enabled. `student_profiles` and `eligibility_checks` have no direct SELECT, INSERT, UPDATE, or DELETE privileges for either `anon` or `authenticated`; `service_role` retains the intended server-side privileges. The authenticated CRUD grants on `scholarships`, `scholarship_sources`, and `account_vault_backups` remain protected by their owner-scoped RLS policies. The browser app still does not read or write student profile or student-specific eligibility rows.

The same audit found `postgres`-owned defaults in `public` do not grant table, sequence, or function privileges to `anon` or `authenticated`. The managed `supabase_admin` default ACL entries still include API-role table, sequence, and function privileges, but a separate ownership query found **zero current tables, sequences, or functions in `public` owned by `supabase_admin`**. Those defaults apply only to objects that the internal role creates; they do not change the ACLs of the existing `postgres`-owned application tables.

Hosted Supabase does not let project owners or the `postgres` database role assume `supabase_admin` or change its default privileges. Do not attempt to grant that membership, use `SET ROLE`, or ship an owner-scoped script that cannot run on the hosted platform. The supported control is to manage defaults for objects created by `postgres` and install extensions in the `extensions` or another non-exposed schema rather than `public`. See Supabase's [managed default-privilege guidance](https://supabase.com/kb/troubleshooting/cant-change-the-default-privileges-of-supabase_admin-in-the-public-schema-448af9). Recheck the managed role's public-schema ownership after extension changes or platform upgrades.

Supabase anonymous Auth users use the `authenticated` role, not the database `anon` role. Keep the existing `auth.uid()` owner checks; do not add broad table policies or grant the database `anon` role access to make anonymous search work.

The existing checked-in legacy schema migration does not match the live schema. Do not apply it. Future migrations require a reconciled migration history and review of current grants and policies.

## Backup handling

New exports use AES-256-GCM with PBKDF2-SHA-256 key derivation, random salt and IV, and authenticated format metadata. Passwords are not saved. Older unencrypted backups remain importable for compatibility with an explicit warning. Backup files are never uploaded by the app.

## Optional analytics

The site includes the first-party consent controller in `public/analytics-consent.js`. Google Tag Manager container `GTM-T6NTTR5X` is requested only after a visitor explicitly enables optional analytics; an unset or denied choice never loads the external tag. The consent decision is stored locally under `scholarship-scout.analytics-consent.v1`. Storage failures fail closed. A persistent Privacy choices control and the Settings page can reopen preferences and withdraw consent. Revocation updates analytics consent to denied and reloads the page. Visitors under 18 are instructed to have a parent or legal guardian make the analytics choice.

The GTM script is restricted to the production apex host; previews and local development do not initialize it. The loader queues Consent Mode defaults as denied, grants only `analytics_storage` after the visitor's affirmative choice, and keeps `ad_storage`, `ad_user_data`, and `ad_personalization` denied. It also enables ads-data redaction. The loader sets static page context (`https://scholarship-scout.org/`, title `Scholarship Scout`, empty referrer) so OAuth callback URLs, query strings, dynamic routes, and document titles are not passed to Google as page metadata.

The only application data-layer event is `scout_page_view` with one fixed `page_type` value from a code-defined allowlist. The adult-owned GTM container should map that custom event to one GA4 `page_view` event with only the `page_type` event parameter. No profile, school, grade, eligibility, scholarship search/filter, form, essay, account identifier, user ID, free-form text, current URL, page title, or referrer is included. The GA4 Google tag must disable automatic page views and Enhanced Measurement; no advertising, remarketing, user-provided data, custom HTML, or unrelated vendor tags may be published. The `page_type` parameter can be registered as a GA4 custom dimension by the adult property administrator. Follow the [adult-owned GTM configuration checklist](google-analytics-gtm-setup.md). Standard Analytics traffic may still involve IP address and browser/network metadata; this is disclosed in the in-product Privacy Notice. The adult account owner must administer the Google Analytics account and container, maintain its configuration and retention settings, and review applicable legal requirements before enabling collection.

Google Analytics contractual terms prohibit sending personally identifiable information and require a Privacy Policy to disclose Analytics use, processing, and cookie/identifier technologies. See Google's [Analytics Terms](https://marketingplatform.google.com/about/analytics/terms/us/), [data safeguarding guidance](https://support.google.com/analytics/answer/6004245), and [Privacy Disclosures Policy](https://support.google.com/analytics/answer/7318509).

## Optional contextual advertising

AdSense support is restricted to one manually placed responsive unit on each of the five public scholarship-guide pages. The application workspace, authentication, profile, discovery, saved-scholarship, application, and API-reference experiences do not include AdSense code. Ads are disabled by default; the first-party loader requires the production apex host, an enabled configuration with valid public publisher and slot IDs, an explicit local opt-in, and an adult/parent/guardian confirmation before it requests AdSense. Preview and local hosts never request the advertising script.

The script requests non-personalized ads (`requestNonPersonalizedAds = 1`) and includes the AdSense teen age-treatment attribute on the ad unit. It does not access or transmit local vault data, profile fields, eligibility inputs, graduation year, state, scholarship search terms, application content, or account identifiers. Google may still use limited cookies or device identifiers for frequency capping and aggregate reporting and may process ordinary browser/network metadata. The preference stored locally is only `granted` or `denied`; storage failures keep ads off. The adult publisher must add and obtain approval for `scholarship-scout.org`, configure a manual ad unit, review consent requirements and category exclusions, and then supply the public IDs. The on-page adult confirmation is an acknowledgement only; it does not verify age or guardian identity and is not a substitute for any consent process required by law or provider policy. Do not enable advertising while those external checks are incomplete.

## Monitoring

The local reliability monitor stores only allowlisted generic event categories and timestamps, retains at most 25 records, and sends no telemetry. It does not store error messages, stack traces, URLs, forms, profile values, or essay content. This local monitor is separate from the optional, consent-gated Google Analytics integration above.


## Platform findings and owner actions

- Security Advisor warns that leaked-password protection is disabled. The app currently uses email magic links and optional Google OAuth, not password login. The project owner should enable leaked-password protection before password-based login is added.
- The deployed `account-delete` function was rechecked on November 28, 2026: ACTIVE version 4, `verify_jwt=true`, with the bounded `readBoundedJsonBody(request, 2048)` reader and shared helper present in the deployed bundle. No real or destructive account-deletion request was used as a smoke test.
- Public live search does not require Anonymous Sign-Ins. Enable anonymous sign-ins only if anonymous cloud scholarship saves are intentionally supported; if enabled, add CAPTCHA/Turnstile and verify the challenge flow.
- CAPTCHA/Turnstile is not yet wired into public discovery. Cloudflare crawler directives are not a bot challenge. Add server-side Turnstile verification before high-volume public launch; do not rely on CORS or client-only challenge checks.
- Define a retention/deletion policy for anonymous Auth users and their owned sponsor rows.
- Anonymous-session email linking is not implemented. Google identity linking is implemented in the app source but requires the Google provider and Supabase manual linking to be enabled; test a real OAuth callback before treating it as available. After successful linking, cloud sponsor rows remain owned by the same Auth user and can be accessed from other devices. Student profiles, essays, and the application workspace remain device-local.
- Migration `20261127052519_restrict_public_default_privileges_for_postgres.sql` manages defaults for objects created by `postgres`; the live audit confirms it does not grant table, sequence, or function privileges to `anon` or `authenticated`. Supabase's `supabase_admin` defaults are internal managed-platform defaults and cannot be changed by a project owner or the project's `postgres` role. The November 28 read-only ownership audit found zero objects in `public` owned by `supabase_admin`, so no current public object is affected by those defaults. The unsupported `supabase/admin/restrict-supabase-admin-public-default-privileges.sql` script and its script-specific test have been removed from PR #26. Keep extension objects in `extensions` or another non-exposed schema; recheck ownership after extension or platform changes. See [Supabase's guidance](https://supabase.com/kb/troubleshooting/cant-change-the-default-privileges-of-supabase_admin-in-the-public-schema-448af9).
- The application HTML retains a restrictive meta Content Security Policy: same-origin scripts, no objects, same-origin base/forms, the known Supabase endpoint for API/WebSocket connections, and the existing Google Fonts origins. Inline styles remain allowed for current React style attributes; inline scripts and `unsafe-eval` are not allowed. `vercel.json` now configures HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and production-only framing restrictions. These source settings still require live response-header verification after an authorized deployment.
- Student records and Supabase session material are now stored as AES-256-GCM ciphertext in IndexedDB after passphrase unlock. The synchronous app storage interface writes to an in-memory map and queues encrypted persistence; failed writes raise a visible warning and prevent the vault from being safely locked until a later write succeeds. The legal receipt and generic reliability events remain plaintext localStorage metadata. The vault does not protect against same-origin script execution while unlocked.
## Privacy requests and support

The in-product Terms of Service and Privacy Notice designate `levi.haidar@outlook.com` as the support and privacy-request contact. Requests are submitted by email using the subjects “Privacy Request” or “Privacy Appeal”; the operator must monitor this mailbox and handle requests to the extent required by applicable law and within the operator’s actual control of the relevant data. A parent or legal guardian may submit a request on behalf of a minor where the applicable law permits.

Settings includes an in-app privacy-request form for access, correction, deletion, covered opt-outs, other privacy concerns, and appeals. It collects only a request category, submitter relationship, reply email, an appeal reference when applicable, and a short description. The form prepares an email addressed to the published privacy contact; the user must review and send that email before a request is received. The draft is not submitted to or stored by Scholarship Scout. The operator cannot retrieve or remotely erase information stored only in the user’s encrypted local vault. Do not request or accept vault passphrases, backup passwords, government identification numbers, or unnecessary student records by email. The public notice deliberately does not publish a residential street address.

Signed-in cloud accounts can be permanently deleted from Settings. The server verifies the supplied bearer token with Supabase Auth and derives the account id from that verified user; the browser cannot nominate another account. Before deleting the Auth user, the endpoint revokes all refresh-token sessions across devices. Previously issued access-token JWTs cannot be revoked immediately and may remain valid until their expiry, but they cannot be refreshed. The verified live database has ON DELETE CASCADE relationships from auth.users to student_profiles, scholarship_sources, scholarships, and eligibility_checks, so deleting the Auth user removes all current account-owned rows in those tables. The app currently has no file-upload path and the live Supabase project has no Storage buckets. Add owner-scoped Storage-object cleanup before introducing uploads or other user-owned external data stores.

The deletion form requires an explicit acknowledgement and the exact text DELETE MY ACCOUNT. A failed session-revocation step prevents Auth-user deletion. A successful cloud deletion is confirmed separately from the local vault operation, so a local cleanup failure is not misreported as a cloud deletion failure.

## Hosting response headers

`vercel.json` now configures site-wide `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, and a restrictive `Permissions-Policy`. The production apex and `www` hosts additionally receive `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`. These framing controls are host-scoped so they do not block the separate Anima preview iframe origins used by the preview application.

The source configuration is not proof of production behavior. Phase 2 does not deploy; fetch the deployed response headers for the apex and `www` hosts and confirm the values before treating the hosting finding as closed. The HSTS policy intentionally omits `includeSubDomains` until every subdomain is independently verified as HTTPS-ready.

The optional local-data action waits for queued encrypted-vault writes, removes the encrypted IndexedDB vault, and clears Scholarship Scout-owned local and session storage plus the app's Supabase Auth session keys in the current browser profile. It preserves unrelated origin storage. It cannot erase another browser profile or device, separately downloaded backup files, or information independently retained by third-party providers. Those locations must be handled separately by the person who controls them.
