# Scholarship Scout — Personal Scholarship Assistant

React + TypeScript workspace for researching, tracking, and reviewing scholarship opportunities, with optional profile filters and official-source review workflows.

> **Current source and release policy — November 28, 2026:** GitHub's `main` branch is the sole canonical application source. Vercel production deployments are built from reviewed commits on `main`. The active application entry point remains `src/App.tsx`; modular refactor files under `preserved-github-work/` are retained but are not wired into runtime. Discovery uses the per-isolate IP limiter and authenticated gateway process ceiling; Upstash is not required. Public scholarship guides, metadata, robots rules, and the XML sitemap are versioned in `public/`. See [repository integrity and release freshness](docs/artifact-integrity.md), [current code-quality audit](docs/code-quality-audit-2026-11-28.md), and [deployment controls](docs/deployment.md).

## Features
- Profile-based scholarship filters using the official transcript and application profile.
- Profile-readiness indicators distinguish high-impact discovery details from optional matching context and explain why missing fields matter without changing eligibility results.
- Profile edits validate ACT (1–36), SAT (400–1600), nonnegative service hours, and numeric GPA. GPA maximums are enforced only when the student explicitly enters a numeric scale, avoiding an assumed 4.0 cap for weighted or district-specific systems. Unchanged legacy values do not block unrelated profile edits.
- Local profile, tracker, and checklist writes report browser-storage failures instead of failing silently.
- Reusable discovery categories cover local, school-resource, regional, state, academic, humanities/major, leadership, community service, language, employment, arts, incoming-college, national, and general opportunities. School and district are optional details entered by the user; no student's school, region, or organization is preloaded.
- Curated reference links point to broad national scholarship search resources and official financial-aid/scholarship-safety guidance. Search results remain unverified leads until a user reviews the current official sponsor page; a search-result domain or directory entry is not treated as sponsor identity.
- Official-source-first discovery records with separate verified, needs-review, and expired states.
- Scholarship records retain sponsor, official URL, award details, exact deadline text/year/time zone when stated, evidence URL/excerpt, and last sponsor-check date.
- Duplicate detection uses normalized scholarship title, sponsor, and deadline year; separate awards on the same program page remain distinct.
- Expired records are separated from current discovery leads; missing deadlines remain unconfirmed rather than being guessed.
- Deterministic eligibility comparisons with pass/fail/unknown outputs remain local; organization memberships and competition-based qualifications are evaluated as separate evidence fields.
- User-initiated encrypted backup export and import include the local profile, scholarship tracker, core checklist progress, and each scholarship's application workspace (custom tasks, essay prompts and drafts, word limits, recommendation request tracking, required-document readiness and deadlines, and final review). New exports use version 3 and browser Web Crypto AES-256-GCM with a fresh IV and PBKDF2-SHA-256-derived key; the password is never stored. Version-1 and version-2 backups remain importable with an explicit unencrypted-file warning for older plain JSON files. Import validates format, workspace records, and scholarship IDs, limits file size and record counts, previews replacement counts, and requires confirmation. Backup files are never uploaded.
- The tracker shows non-destructive near-duplicate suggestions only when the sponsor and deadline year match and scholarship titles are highly similar; nothing is merged or deleted automatically.
- Each scholarship has a separate manual application status (Not started, Preparing, Ready, Submitted, Awarded, Rejected), personal priority, tags, submission date, decision date, and archive state. Eligibility status remains separate, and archived records can be restored without deleting history.
- Tracker views support independent eligibility/application/archive filters and sorting by deadline, priority, award amount, application status, eligibility, or name. These manual workflow fields remain local and are included in encrypted backups, not cloud sponsor rows. On small screens, opportunities become labeled cards with keyboard-operable review controls. The tracker also supports a user-initiated CSV report download; it keeps application status and eligibility separate and neutralizes spreadsheet formula-like cell prefixes.
- The Overview dashboard and tracker show date-only deadline urgency (overdue, due today, due within seven days, upcoming, or unconfirmed) without inferring sponsor cutoff times or time zones.
- Scholarship details include a sponsor-evidence completeness checklist. It identifies missing source details, evidence excerpts, deadline evidence, unsafe links, or stale sponsor checks; it is explicitly separate from personal eligibility.
- Eligibility details group passed, failed, and unknown requirements into a plain-language summary. Unknown items remain unknown; the summary does not promise an award or infer missing sponsor conditions.
- Application prep provides a separate workspace for each tracked scholarship: custom steps, the sponsor's exact essay prompts, private draft text and live word counts, recommendation status/request/due/received dates, transcript/résumé and custom document checklists, document deadlines, and a final review list. Suggested documents begin optional and are counted only after the student marks them required. Submission and decision records remain manual; recording Submitted asks for confirmation and does not send anything to the sponsor. Workspace records are encrypted in the passphrase-protected local vault in IndexedDB, are included in user-controlled encrypted backup files, and are excluded from search payloads and cloud sponsor rows. Signed-in users can unlock a remembered browser automatically after account authentication using a non-exportable device key. A new browser or device can restore the optional account backup with a synced WebAuthn PRF passkey or the recovery passphrase; guest users continue to use their local passphrase. The vault locks after 15 minutes of inactivity and can be locked manually from Settings.
- Public live scholarship search can be used without creating an account or a Supabase Auth session. Google OAuth and email magic links are supported for cloud scholarship records. Permanent signed-in accounts can optionally enable a separate end-to-end encrypted cross-device vault backup; it is off by default, unavailable to guest/anonymous sessions, excludes the Supabase auth session and PKCE verifier, and uses a synced WebAuthn PRF passkey or the local vault recovery passphrase. An existing anonymous cloud account can be converted to a Google-backed account through Supabase identity linking without changing its row owner; public discovery does not create anonymous Auth users.
- Toggleable light/dark appearance, saved locally in browser storage.
- Responsive two-column grouped mobile navigation, a skip-to-content link, keyboard-visible focus, screen-reader status announcements, a locally persisted compact/comfortable layout toggle, and an offline banner. Local work remains available when disconnected; cloud sign-in and live search are disabled until the connection returns. Scholarship editor, detail, and backup dialogs include dialog semantics, focus entry/trapping/restoration, and Escape handling. Client reliability diagnostics stay local, record only generic event categories and timestamps, retain at most 25 entries, and send no telemetry; a recoverable error boundary handles render failures.
- Additional optional profile context for manual search links: academic strengths, career interests, awards/honors, preferred college location, enrollment plan, and broad search keywords.
- User-scoped scholarship sponsor records in the existing `public.scholarships` table, protected by existing RLS policies. The owner can be either a pseudonymous anonymous Auth user or a permanent signed-in user.
- Public live scholarship discovery uses the token-protected SearXNG gateway and accepts only state, graduation year, and selected category IDs; results remain unverified leads until official sponsor review. The selected limiter design does not require Redis: the Edge Function applies a two-per-minute per-IP isolate limit and the authenticated single-process gateway caps upstream requests at 30 per minute across Edge Function isolates. The gateway's ceiling is process-local and does not include a global concurrency lease or daily per-IP quota. Supabase `scholarship-discover` is ACTIVE at version 29 and all five deployed files matched GitHub `main` at baseline SHA `28137158d8beb3243da295e3f4ffaf6676edfbd0`. The active `account-delete` v4 entrypoint is executable-equivalent to `main` after comment removal, and its shared body reader matches byte-for-byte. Upstash remains optional code only and is not used by the wrapper. See `docs/code-quality-audit-2026-11-28.md`.

The project contains `student_profiles`, `scholarship_sources`, `scholarships`, `eligibility_checks`, and the opt-in `account_vault_backups` ciphertext table, all with RLS enabled. The browser client uses the existing project URL and the public publishable key. Publishable keys are intended for browser use and are not secrets; never put a service-role/secret key in frontend code or a `VITE_` variable. Account authentication material is encrypted in a separate device-key-protected IndexedDB store and is excluded from cross-device vault snapshots.

The application reads and writes owner-scoped scholarship sponsor records in `public.scholarships`; permanent accounts that explicitly opt in also read/write their own encrypted `public.account_vault_backups` row. The backup contains encrypted local-vault ciphertext and passkey metadata only, not the Supabase auth session or PKCE verifier. The scholarship-record identity may be an anonymous browser session or a permanent account. Student profile data and student-specific eligibility results stay in the local vault by default. If cross-device backup is explicitly enabled, the full vault is included only as client-encrypted ciphertext; these records are not uploaded as plaintext or as separate profile/eligibility rows. The Discovery page builds Google search links from state/county, education level and graduation year, planned college and major, interests, and the optional profile search fields; query terms are sent only after the user clicks a Search link. GPA, rank, test scores, citizenship, and membership fields are used for local comparisons against scholarship rules already entered in Scout, not automatically sent to Google. The app does not currently write to `student_profiles` or `eligibility_checks`.

Supabase reports `scholarship-discover` ACTIVE at version 29 with `verify_jwt=false` for public discovery only. Its five deployed source files match GitHub `main` at audit baseline SHA `28137158d8beb3243da295e3f4ffaf6676edfbd0`. `account-delete` is ACTIVE at version 4 with `verify_jwt=true`; its entrypoint is executable-equivalent to `main` after comment removal, and its bounded-body helper matches exactly. Google sign-in requires the Google provider credentials to be configured in the existing Supabase project as described below; no Google client secret belongs in frontend code.

No private school files or user-owned scholarship spreadsheets are included in this public source artifact. Scholarship records should be added only after checking their current official sponsor pages.

## Setup
1. Use Node.js 26.13.x (the exact version in .nvmrc; package.json requires Node >=26 and <27), then run `npm ci` to install the exact versions from `package-lock.json`.
2. Use the existing Supabase project `wjrwvempgjvoxlioodse` in `us-east-1`; do not create another project.
3. Supply its publishable key as `VITE_SUPABASE_PUBLISHABLE_KEY` in the artifact's build environment. The project URL is already the default in `src/lib/supabaseClient.ts` and `.env.example`.
4. Public live discovery does not require Anonymous Sign-Ins. Enable anonymous sign-ins only if anonymous cloud scholarship saves are an intentional supported workflow; otherwise keep the sign-in surface limited to the configured permanent-account flow.
5. If anonymous sign-ins are enabled, configure CAPTCHA/Turnstile before public rollout and verify the challenge flow. Public discovery currently uses the per-isolate IP limiter plus the authenticated gateway's 30-request-per-minute process ceiling; this is not a durable daily-quota system or a shared concurrency-lease system.
6. Configure Supabase Auth's allowed return URLs for the actual deployed frontend origin for both email magic links and Google OAuth.
7. Do not apply the archived `supabase/legacy/202611090001_scholarship_scout.sql` file. It targets the former `scholarship_profiles` / `scholarship_opportunities` model and is not compatible with the existing project's tables. The active `202611100001_restrict_anon_privileges.sql` file only mirrors the grant revocations already applied to the existing tables.
8. Add `SEARXNG_GATEWAY_URL` and `SEARXNG_GATEWAY_TOKEN` under Supabase Edge Function Secrets. The URL is the current HTTPS tunnel base address without `/search`; the token must match your local `%USERPROFILE%\\searxng-local\\gateway\\gateway-token.txt` file. Do not place either value in a frontend environment variable.

Use only the publishable key in the browser build environment. Never place a service-role key, SearXNG gateway token, or other secret in frontend code or a `VITE_` variable. The browser integration uses the current Supabase Auth identity and existing owner-scoped RLS policies. Anonymous Auth users also use the Postgres `authenticated` role and are isolated by their unique `auth.uid()`. This hardening pass revoked anonymous table/sequence privileges and removed non-row-scoped table permissions from authenticated users; it did not change table schemas or RLS policies. The discovery Edge Function is public for discovery only (`verify_jwt=false` on this function); it performs no database writes. Cloud scholarship CRUD remains authenticated and owner-scoped.

### Google sign-in setup

The Google button is implemented in the app, but OAuth will not complete until the provider credentials are configured in the existing Supabase project:

1. In [Google Auth Platform](https://console.cloud.google.com/auth/clients), create an OAuth client with application type **Web application**.
2. Add `https://scholarship-scout.org` as an authorized JavaScript origin. Add any editor-preview or local-development origin only when you intentionally test that exact origin.
3. Add this exact authorized redirect URI in Google: `https://wjrwvempgjvoxlioodse.supabase.co/auth/v1/callback`.
4. In [Supabase Auth Providers](https://supabase.com/dashboard/project/wjrwvempgjvoxlioodse/auth/providers), enable Google and enter the Google OAuth Client ID and Client Secret. Keep the secret in Supabase only.
5. Enable **Manual Linking** in the Supabase Auth provider/security settings. Scholarship Scout uses `linkIdentity()` for a current anonymous account so its existing `auth.uid()` and cloud sponsor rows stay attached to the same user.
6. In Supabase Auth URL Configuration, set the production Site URL to `https://scholarship-scout.org/` and allow that exact return URL. Add only exact preview/development return URLs that are actually required; do not use broad wildcards.

The browser requests only `openid email profile` for Google authentication. It does not request Gmail, Drive, or other Google API access. The OAuth callback uses PKCE and the encrypted local-vault storage adapter; the same browser profile must remain available until the callback has completed.

## Cloud data boundary
- Cloud reads and writes are limited to the active Supabase Auth user's scholarship sponsor records in `public.scholarships`; permanent users may also explicitly opt in to their own end-to-end encrypted `public.account_vault_backups` row. Anonymous users cannot access the backup table.
- The saved fields are scholarship title, sponsor, official HTTPS URL, award range/text, deadline, structured sponsor eligibility criteria, currency, and verification status.
- Free-form notes and source excerpts are excluded from structured cloud sponsor rows. The official source URL and safe supporting-rules URL are retained as evidence references; source authority, deadline display/time-zone text, and last-checked date are retained in the scholarship's structured `eligibility` JSON. Public evidence excerpts remain local to avoid accidentally including them in sponsor records. If the user separately enables cross-device backup, local vault content is included only in its encrypted envelope.
- Student profiles, contact details, academic records, activities, essays, and student-specific eligibility assessments stay in the encrypted browser vault by default. They are not sent to search or stored as plaintext cloud rows; an explicit cross-device backup uploads only an end-to-end encrypted vault envelope.
- The application does not currently use `student_profiles` or `eligibility_checks`.
- Supabase reports `scholarship-discover` ACTIVE at version 29 with `verify_jwt=false` for public discovery only. The browser sends only state, graduation year, and selected category IDs; the function does not read or write `student_profiles`, `scholarships`, or `eligibility_checks`. All five deployed discovery files match GitHub `main` at the audited baseline. The no-Redis per-isolate limiter plus authenticated gateway ceiling remains in place. `account-delete` v4 has executable source parity with `main` after comment removal and an exact shared body-reader match; see `docs/code-quality-audit-2026-11-28.md`.
- The deployed function sends only state, graduation year, and selected category terms to the SearXNG gateway. It does not read or write `student_profiles`, `scholarships`, or `eligibility_checks`.
- Existing RLS policies restrict each of the four tables to authenticated rows owned by `auth.uid()`. Do not disable RLS or add broad policies to make integration work.

## Evidence and source-status rules
- `verified`: an HTTPS official sponsor/program/school source, sponsor identity, award details, deadline (or an explicit sponsor statement that no fixed deadline exists), eligibility evidence, and a sponsor-check date within the previous 30 days are all present.
- `needs-review`: the item is a lead, the source is a directory/secondary listing, a required field is missing, or the last sponsor check is older than 30 days.
- `expired`: the recorded deadline date is earlier than the current local calendar date. Date-only deadlines are not treated as expired during the stated calendar date.
- Discovery dates are not substituted for sponsor-check dates. Unknown deadlines are labeled “Deadline not confirmed”; no time zone is inferred when the sponsor does not state one.
- A verified source label describes the listing evidence, not the student's eligibility. Eligibility checks keep unknown requirements unknown.
- Sponsor eligibility details are retained as source-linked evidence and should be rechecked against the official program page before a student relies on them.
- Organization membership, achievement credentials, and competition awards are evaluated separately; one credential should never be treated as proof of another.

## Privacy and security review checkpoint
- The browser client exposes only the Supabase project URL and publishable key. These are public client configuration, not secrets. No service-role key or third-party provider secret was found in the checked-in frontend source or `.env.example`. Never put a secret in a `VITE_` variable.
- Cloud API methods call `auth.getUser()` before database operations and scope scholarship queries/updates by the returned user's `owner_id`. These client filters are defense-in-depth only; the existing database RLS policies are the actual authorization boundary.
- Cloud rows returned from the database are untrusted. The mapper rejects unsafe/non-HTTPS sponsor and evidence URLs (including localhost and numeric IP hosts) before they reach clickable cloud-result links. The UI and cloud-save mapper apply the same public-HTTPS checks.
- Magic-link redirects use the current Scholarship Scout app origin. Supabase Auth should allow only the production app URL plus explicitly required local development URLs; do not configure broad wildcard redirect URLs.
- Supabase JS persists and refreshes the authenticated session in browser storage. This is persistent, not permanent: revocation, sign-out, security events, or expiration can still require a new email link.
- The profile, tracker, and application workspace are encrypted at rest in the local IndexedDB vault using AES-256-GCM and the passphrase-protected content key. Supabase Auth session/PKCE material uses a separate IndexedDB store protected by a non-exportable device key and is not synced with the account vault. A same-origin script can still read decrypted student records while the local vault is unlocked. The legal acceptance receipt and generic reliability history remain localStorage metadata.
- Student-specific GPA, class rank, test scores, school, activities, and related personal defaults have been removed from the shipped app source. Values already saved by the user in this browser's `scout-profile` storage remain loadable.
- Public discovery is intentionally callable without a Supabase Auth session (`verify_jwt=false` on this function only); it uses server-only SearXNG gateway secrets, validates result URLs, and does not access database tables. Cloud scholarship CRUD remains authenticated and owner-scoped. The gateway requires a bearer token and accepts only the bounded `/search` route. CORS headers are not an authorization mechanism. The current production gateway route still needs secure secret reconciliation and a fresh end-to-end check; see the [current code-quality audit](docs/code-quality-audit-2026-11-28.md).
- The SQL migration `202611100001_restrict_anon_privileges.sql` mirrors the successful existing-table grant changes. Existing anonymous table privileges and sequences were revoked; `authenticated` retains CRUD subject to the existing row-owner RLS policies, while `TRUNCATE`, `REFERENCES`, `TRIGGER`, `MAINTAIN`, and direct sequence access were removed. The SQL role could not alter global default privileges, so future table grants still need a database-owner review.
- Scholarship applications are never submitted automatically. Search links open only after a user clicks them; no transcript, résumé, contact details, or identifying profile fields are sent to search providers or sponsors automatically.
